# PREFLIGHT

Every defect found while building Blink, with the number that exposed it and the number after the fix.
A row is closed only when its number after is measured. Tests that lock a row name it in their docstring.

| # | what was wrong | the number that showed it | fix | the number after |
|---|---|---|---|---|
| PF01 | C: is the fast drive but nearly full | 25 GB free of 464 GB | repo and venv on C:; all data, caches and runs under `BLINK_HOME=D:\blink`; uv cache on D: | C: 23.0 GB free after the torch 2.14 cu130 install (doctor floor 12 GB) |
| PF02 | free VRAM is not a constant: desktop apps hold part of the 8 GB | 6.3 GB free on one read, about 4.9 GB on another | doctor measures `torch.cuda.mem_get_info()` and sizes batches from it | doctor: 7.46 GB free at 14:05, budget 6.66 GB (free minus 0.8 GB) |
| PF03 | the default PyPI torch wheel for Windows is CPU-only | a plain install gives `+cpu` | explicit cu130 index for win32 in `pyproject.toml` | `uv.lock` pins `download.pytorch.org/whl/cu130` (3 entries); doctor reports `2.14.0+cu130` |
| PF04 | torch.compile on Windows needs the community triton-windows fork, paired by minor version | torch 2.14 pairs only with Triton 3.8 | pin `triton-windows>=3.8,<3.9`; compile stays optional | inductor + triton-windows 3.8.0.post28 compiled a GELU kernel on the 3070 |
| PF05 | torch 2.14 on Windows builds no flash attention kernel | `USE_FLASH_ATTENTION` excludes MSVC at v2.14.0 | use the memory-efficient SDPA kernel in bf16 | doctor: efficient SDPA bf16 True, flash SDPA False, capability (8, 6) |
| PF38 | a detached job must outlive the agent session that launched it | unknown until tried | heartbeat probe launched with `Start-Process` from a shell that exited at once | 120 beats over the full 20 minutes after its launcher exited; long runs will use `Win32_Process.Create` so they also sit outside any session job object |
| PF39 | a redirected stdout on Windows uses the ANSI code page, so one Hebrew or sigma character kills a run | the unguarded print exits non-zero (`test_without_the_reconfigure_a_redirected_print_crashes_on_windows`) | `configure_stdio()` forces UTF-8 on stdout and stderr | exit 0 and the exact UTF-8 text (`test_cli_survives_non_ascii_output_when_redirected`) |
| PF40 | the 22.09 GB eval DB over one connection | 1.1 MB/s, 334 min estimated | 4 parallel range workers (each connection is capped at about 1.2 MB/s) | 21.36 GB in 94 min, 3.79 MB/s aggregate while sharing the line with the torch download (3.4x one stream) |
| PF41 | Lichess answers 429 above about 5 connections, and a naive range appender wrote the 429 HTML page into the data | 2 of 6 segments held a 162-byte nginx page | 64 MiB chunk files, each kept only on HTTP 206 with the pinned ETag and the exact byte count | 4 of 320 chunks got a 429 and succeeded on retry; the assembled 22,086,532,809 B file matches the published sha256 `234f36f9...2b65` |
| PF42 | stopping a background shell left its subshells alive; they restarted curl and kept appending to renamed files | 4 pieces grew by 36.5 to 44.0 MB after "stop" | kill the whole process tree by PID; trim each piece to its planned offset; check that pieces tile the file exactly | pieces tiled [0, 22,086,532,809) exactly and the sha256 matched |
| PF43 | with torch in a uv extra, any plain `uv run` would uninstall it (uv syncs exactly) | found in review before it happened | torch and triton moved to default dependency groups; the torch-free CI leg opts out | `uv run` keeps torch |
| PF44 | escape sequences written into the punctuation test became the very characters it bans | the test flagged its own file (7 characters) | build the banned characters from code points with `chr()` | the test passes on every tracked file |
| PF29 | `torch.onnx.export(dynamo=True)` writes weights to a second file by default, which a static page cannot load as one model | the default export gives 2 files | `external_data=False` and `opset_version=20` passed explicitly; `check_self_contained()` refuses anything else | one 2,219,744 B file, opset 20, 0 external initializers; torch vs onnxruntime max difference 5.72e-6 on 1,000 positions |
| PF45 | the eval DB holds Chess960 positions, whose castles are illegal in standard chess | all 77 illegal best moves in the first 20 frames are Chess960 castles | rejected with a reason code today; P2 gives them their own code and a count | 40 rejects in 673,704 packed lines, 0 other errors |
| PF46 | a checkpoint interval of 0 steps was accepted and crashed at step 1 | `ZeroDivisionError` on the first step | config load refuses non-positive intervals | 4 refusal tests pass |
| PF47 | on Windows an open read handle (the live dashboard) makes `os.replace` fail, so checkpoints and logs could not be saved while someone watched | `WinError 5` with the real files held open | every atomic writer retries 10 times, 0.2 s apart | resume succeeded while another process made 17,416 reads of the logs |
| PF48 | `node --test site/tests` treats the folder as a module on Node 22 | 1 pseudo-test fails with MODULE_NOT_FOUND | run `node --test "site/tests/**/*.test.mjs"` | 7/7 pass |
| PF49 | chess.js keeps castling rights and en-passant squares that python-chess cleans away, so the browser tokenizer could disagree with training | 3 golden castling FENs and 5 en-passant FENs differ before the fix | the JS tokenizer cleans rights and keeps only legal en passant, like python-chess | JS equals Python on 50/50 golden positions |
| PF50 | chess.js's ESM build is 3,368 lines, over the 800-line house limit for tracked source | the hygiene test fails on it | not vendored: served from node_modules locally and copied in at deploy | hygiene tests pass |
| PF51 | cm-chessboard's source contains an ellipsis and em dashes the house text rule bans | 1 ellipsis and several em dashes in 3 files | vendor only the 9 core modules, with ASCII punctuation; a test proves nothing else differs from npm | punctuation test passes |
| PF52 | Wikimedia's API labels the cburnett pieces CC BY-SA 3.0 | LicenseShortName says CC BY-SA 3.0 | the file pages offer GFDL, BSD and GPL; `LICENSE-pieces.txt` elects BSD 3-Clause | licence test passes |
| PF53 | the page counted a reply before its arrows were drawn, so the smoke test read the board mid-animation | 0 arrows seen after the 10th reply | count a reply only after the move, arrows and win bar are rendered | at least 3 arrows after every reply |
| PF54 | the Lichess bot config starts `blink-uci.exe`, but the project never declared that script | the venv had `blink.exe` only | `blink-uci = "blink.uci:main"` in `[project.scripts]` | the built wheel lists both scripts; the launcher answers uci/isready/go |
| PF55 | fastchess waits 10 s by default for an engine's first uciok/readyok, and a loaded machine starting several torch+CUDA Blink engines at once needed longer | 3 of 20 skeleton gauntlet games scored as crashes ("not responsive"); one cold start takes 7.3 s alone and 9.6 s with 6 at once | `-startup-ms 60000` in every gauntlet (test-locked); Blink's play does not depend on this wait | 20/20 games, 0 forfeits, 0 crashes, 595 decisions, 0 no-search violations |
| PF56 | gradient clipping at 1.0 is always on for this loss: the gradient norm sits far above it | skeleton run: grad-norm median 5.93 (0.94 to 7.13), clip fraction 0.98, which would trip the P7 "clip fraction >= 20%" stop rule | P4 recipe measures the norm over warmup and fixes the clip at 2x its 95th percentile | pending: P4 |
| PF57 | the first public CI run failed: three site tests still exercised the loader's old fallback, and a test assumed the build machine's CPU count | Windows leg: 4 failed, 339 passed (GitHub's runner has 4 CPUs, the test demanded 5) | the loader tests now pin the real interface; worker count is `default_procs()` (cores minus one, at most 5); before every push the full suite runs in the GPU venv and in the torch-free venv, never a subset | GPU venv 512 passed; torch-free venv 348 passed, 8 skipped |
| PF58 | Windows has no memory overcommit: each CUDA Python process commits about 4.3 GB of RAM or page file, even for a tiny model, so parallel GPU jobs balloon the page file on C: | C: free fell from 23 GB to 8.4 GB with 6-8 CUDA processes running, then recovered on its own; 2 processes committed 8.7 GB | cap concurrent CUDA processes per phase; doctor keeps a 12 GB floor on C:; 15.18 GB of old caches cleared with Itay's approval | 39.24 GB free on C:; commit 34.3 of 41.4 GB with 2 CUDA processes |
| PF59 | the eval DB is not the game distribution: it over-represents forced mates | 17-22% mate share in eval-DB frames vs 9.9% in 10,000 held-out real-game positions (games10k, SF19 at 1M nodes, 76 min on 5 processes) | rebalancing weights toward the game histogram; games10k is the external test set | pending: P5 arm a07 judged on games10k |
